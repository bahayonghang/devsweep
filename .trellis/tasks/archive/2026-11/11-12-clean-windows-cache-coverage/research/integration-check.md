# 四个浏览器缓存通道的独立复核

2026-11-20，在 Windows 集成工作树 `D:/ds-integrate-1120` 核对，输入版本为 `264e7ac` 和 `324e72b`，包含同日的 R6 未提交修改。

| 验收 | 复核结果 |
| --- | --- |
| AC1 登记、边界与占用 | 四个通道各自只取默认根下已登记 profile 的两个直接子目录。核对了固定目录、同品牌共享进程名、未知或运行中时的零目标和重扫提示。Windows 枚举失败或不完整返回 Unknown。实际执行使用同一规则按路径重读元数据、所有者状态和文件树。 |
| AC2 规则清单 | 独立重跑 CLI 黑盒用例，逐一核对四个 ID 的 JSON、中英文列表与详情。另从 CLI 正常入口读取中文 Edge Dev 说明，其中明确写出关闭所有通道再扫描。 |
| AC3 排除项 | 独立检查明确列出的八条遗漏、Docker 与 Cargo home 的断言。集成测试的覆盖遗漏、正常扫描至保存计划再到记录式执行、隔离重命名三个用例通过。 |
| AC4 界面 | 从两个已构建的独立测试程序复验，TUI TestBackend 列表与 GPUI 全局分组/双语辅助标签各通过一项。渲染夹具不访问宿主浏览器。 |
| AC5 工程门禁 | 父任务串行运行完整 `just ci` 并在归档前登记结果。定向测试不能代替此项。 |

复核时发现已登记配置表只读取名称。即使该名称对应的 JSON 值为 null，只要存在 Preferences，就会给它的两个缓存目录授予资格。新夹具复现此行为。已在四个预发布通道将登记条目校验收紧至 JSON 对象，异常 profile 保留明确的 OwnershipUnknown，另一个有效 profile 仍被识别。同一解析逻辑覆盖发现与计划的实时核验，规范已同步。夹具与记录执行器未操作已安装浏览器的数据。

初次带有 null 登记的回归在 Chrome Beta 发现 4 个候选，期望只有健康 profile 的 2 个。原始失败保存在本次工作树的 `dist/verify-1120/r6-corrupt-registration-red.log`。

修复后，该核心模块 11 项测试全部通过，包括四个通道的损坏登记与健康同级隔离。结果见本次工作树的 `dist/verify-1120/r6-corrupt-registration-green.log`。本次修改的 Rust 文件通过 rustfmt，变更通过 git diff --check。
